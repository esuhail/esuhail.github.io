LLM Bench

Check which AI models your graphics card can run, and how fast, before downloading them.

Open the live site Read the code

Python, FastAPI, PostgreSQL, SQLite, plain JavaScript, Ollama, GitHub Actions, Render

Why I built it

Local AI models are multi-gigabyte downloads, and you can't tell whether one runs well on your card until you've already downloaded it. I wanted a site someone who only knows the names ChatGPT and Claude could use: pick your graphics card, see what fits, see how fast it will answer.

How the speed estimate works

Writing one token means reading every active weight from graphics memory once, so speed is mostly limited by memory bandwidth. My first formula made a 0.6B model look half as efficient as a 9B model on the same card. Adding a fixed cost of about 1 ms per token fixed it: both came out near 55% efficiency.

time per token = model size ÷ (efficiency × bandwidth) + 1 ms

Try the estimator

This is the same formula the site uses, running in your browser with the default efficiency. The live site replaces it with efficiency learned from real benchmarks.

Getting numbers I could trust

Each model answers 3 prompts, 3 times each, with the same settings. The first runs were wrong in ways that weren't obvious:

The first run included the time to load the model
A warm-up run before measuring.
Ollama cached prompts, so repeat runs looked faster
A unique prefix on every prompt.
Thinking models generated thousands of hidden tokens
Turned thinking off for benchmarks.
One model ran about 4% slower because of its own sampling default
The same sampling settings for every model.

How I know it works

  • 22 pytest tests run on every push with GitHub Actions.
  • Estimates are checked with leave-one-out testing against real benchmark results.
  • The download and benchmark endpoints only run on your own machine and reject requests from other sites.

Duel

Quick 1v1 minigames against a friend, best of 3 or 5, from a 4-letter room code. No accounts and no game server.

Play Duel Read the code

TypeScript, React, Vite, WebRTC (PeerJS), Vitest, Playwright, GitHub Actions, GitHub Pages

Why I built it

I wanted something my friends and I could open on our phones and play right away. Hosting a game server costs money and needs upkeep, so the host's browser is the server and the two phones talk directly over WebRTC. It costs nothing to run.

Decisions that made it work

Lag shouldn't decide who wins
Both phones build the same puzzle from a shared seed (mulberry32) and play it locally, then send one score. Nothing crosses the network during a round.
Both players need to start at the same moment
The guest pings the host 5 times, keeps the fastest round trip, and estimates the clock difference. The 3-2-1 lands within about 20 ms.
Syncing whole game states is fragile
The match rules are one pure reducer that runs on both phones. The host sends the event it just applied, not the new state, so messages stay tiny.
Phones drop connections
A heartbeat notices a lost player within about 8 seconds, the guest retries the same room, and the host waits 30 seconds before calling a forfeit.

How I know it works

  • 48 Vitest tests: every game's puzzle reproduces from its seed, plus ties, forfeits, rejoins and garbage messages.
  • 7 Playwright tests open two browser windows and let bots play full matches, then a rematch.
  • A real match between a phone on cellular data and a laptop on home Wi-Fi.
  • CI runs on every push and deploys to GitHub Pages.

Known trade-offs

The host runs the rules, so a determined host could cheat. That's fine between friends. A ranked mode would move the host logic to a server, and it only depends on one connection interface, so that's a transport swap rather than a rewrite.

Canvas Grade Companion

A Chrome side panel that recalculates your Canvas grades, checks them against Canvas's own totals, and tells you what you need on the work that's left.

Read the code

TypeScript, React, Chrome extension (WXT), Vitest, Playwright, GitHub Actions

Why I'm building it

Canvas shows a total but not how it got there, and it can't answer the question students actually have: what do I need on the final? This panel works that out, and it only calls a number verified when it matches what Canvas reports.

What it does

Verified grades
Recalculates every course total, including weighted categories and drop rules, and compares it with Canvas. On a real GMU account, every course with a reported total came out verified.
Target solver
Pick a target grade and it answers in one sentence: the average you need on what's left, that you're already safe, or that the target is out of reach and what the ceiling is.
Up next
One list across all courses, ranked by how much each item is worth and how soon it's due.
Syllabus check
Reads grade weights and dates from a syllabus PDF and shows where it disagrees with Canvas.

How I know it works

  • 190 Vitest unit tests. Drop rules are checked against a brute-force version, and every solver answer is fed back through the grade engine.
  • An end-to-end test loads the built extension in Chrome against a stand-in Canvas server, and asserts it only ever sends read requests.
  • Read-only by design: no server, no account, no access token. Nothing leaves the browser.
